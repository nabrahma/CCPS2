# Decisions

Non-obvious technical choices and every place where the PRD turned out to be wrong or incomplete (PRD rule 4 and rule 6). Newest at the bottom.

| ID | Decision | Reason |
| --- | --- | --- |
| D-001 | Base mesh, targets, modifiers, default rig and face pose units come from the MakeHuman 1.x repo at `a8bc2d54`. The GameEngine rig, its weights and the hm08 vertex-group table come from MPFB2 at `6ff1eb35`. Clothes, hair, brows, lashes, eyes, teeth and skins come from the CC0 asset packs. All sources are pinned by SHA-256 in `tools/asset-compiler/sources.lock.json`. | The golden oracle (MakeHuman 1.x Python) must run on exactly the data the engine uses. The GameEngine rig is not in the MakeHuman 1.x repo or the system-assets pack, only in MPFB2. |
| D-002 | The asset compiler runs on Python 3.12.5 (PRD says 3.11). | That is the installed interpreter; the compiler only uses numpy and Pillow, which are pinned in `requirements.txt`. |
| D-003 | The PS2 body meshes and garment decimation are built in Node (`tools/asset-tools`, meshoptimizer 1.3.0 JS/WASM), not in the Python compiler. | The PRD names the meshoptimizer JS/WASM build. This also reuses `@ps2cc/core` (base mesh loader, normals, MHCLO) instead of a second implementation. |
| D-004 | Target deltas are stored as int16 with a per-target scale (45 MB instead of 80 MB as float32). Worst-case error is max\|delta\|/65534, about 5 µm per target. | MakeHuman's own compiled `targets.npz` also uses int16 (with a coarser fixed step). The error is far below the 0.1 mm golden tolerance. |
| D-005 | **PRD correction:** MakeHuman 1.x loads 291 modifiers (modeling + bodyshapes + measurement) that reference 1,095 target files. The PRD says "about 249 modifiers / 1,258 targets". | Counted from the pinned data. The extra `.target` files in the repo (expressions, proxies) are not referenced by any modifier. |
| D-006 | Modifier values are stored explicitly in the CharacterDoc, and target weights are derived as a pure function of (macros, modifier values). | Verified at compile time: no non-macro target depends on a macro variable (`assets/core/targets/registry_report.json`), so MakeHuman's detail-stack propagation reduces to this function. Golden tests check the weights per target. |
| D-007 | UV seams are hard-locked only on the head, face and hands of the PS2 body. On the torso and limbs, meshoptimizer's own seam handling keeps them watertight. | Locking all 2,259 seam vertices made the 8k tier unreachable. meshoptimizer never collapses across a seam, so seams stay exact either way. |
| D-008 | Blender's `vec_roll_to_mat3` is ported with the exact `1 + y` term in float64. Blender's float32 series approximation is used only when `1 + y < 1e-12`. | Blender's approximation leaves the toe bones about 1e-5 non-orthonormal, which broke exact rest-pose skinning. |
| D-009 | Golden GameEngine joint positions are computed by applying MPFB's documented strategy (mean of joint-cube or listed vertices, plus offset) in numpy to the MakeHuman oracle's morphed mesh. Golden default-rig joints come from MakeHuman's own `skeleton.py`. | MPFB's rig code needs Blender (`bpy`), which is not allowed (Fixed decision: no Blender). |
| D-010 | The adult age floor (18 years, age = 0.354) is enforced everywhere: engine, curated view, the All sliders view, loading and presets. | PRD: "all characters are adults". Product rules win over MakeHuman's ranges (PRD 8.3). |
| D-011 | Genital modifiers, nipple detail and pelvis bulge are hidden and never randomized. Skins and garments whose names mark explicit content (genitals, nude, thong, special_suit) are excluded at compile time (`catalog_skipped.json`). | PRD non-goal: no nudity or anatomical detail beyond underwear level. |
| D-012 | Viewport lighting is computed in linear space; the post pass converts to sRGB and then applies dither, grain and the other effects. | Unity 6 URP projects default to linear colour space, so the preview matches what Unity shows. 16-bit dithering belongs in display space. |
| D-013 | Hide-body-under-garment follows MakeHuman on the full-density hm08 body: a face is hidden if any of its vertices is in the garment's `delete_verts`. **Superseded for PS2 bodies by D-025.** | Same rule as MakeHuman's vertex mask, so CC0 garments look as their authors intended. |
| D-014 | Garment decimation accepts "no **new** flips". It falls back to unlocked borders, then pruning tiny disconnected parts (< 1.5% of the garment's size), when a garment cannot reach its budget. | Many CC0 garments already have inconsistent winding or thin double layers (up to 94 "flipped" triangles in the original). Shoes and gloves made of many small open pieces cannot be reduced with locked borders. |
| D-015 | zustand is pinned to 5.0.16 instead of 5.1.0. | 5.1.0 was younger than pnpm 11's minimum release age; we keep the supply-chain policy rather than add an exception. |
| D-016 | TypeScript is pinned to 5.9.3, not 7.x. | typescript-eslint 8.72 supports TypeScript < 6.1. |
| D-017 | **PRD correction:** the "Faceunits 01" and "Visemes 01/02" packs return 404 on the asset servers. Expressions (M8) will use `face-poseunits.bvh` and the expression definitions shipped in the MakeHuman 1.x repo. | Checked on 2026-11-07. MakeHuman community services were announced as shut down on 2026-10-21; the remaining downloads still work but may disappear, which is why every archive is checksum-pinned. |
| D-018 | The installed gcc is MinGW.org 6.3 (32-bit), which cannot build ufbx with cgo for windows/amd64. A 64-bit mingw-w64 toolchain must be added before M7 (see `TOOLCHAIN.md`). | The PRD requires ufbx read-back tests in `go test`. |
| D-019 | Licence of borrowed logic: the TypeScript engine is a clean implementation that follows MakeHuman's algorithms (comments name the ported functions); no AGPL code is copied. The golden oracle runs unmodified MakeHuman code from the download cache and is never shipped. `vecRollToMat3` follows Blender's (GPL) algorithm. | PRD 3 allows this for an internal tool. It must be re-checked before PS2CC is ever distributed (PRD 9.2). |
| D-020 | The 8k body tier thins the face lightly (97% of face vertices kept, above the PRD's 90% floor) so that at least a third of the budget is left for the body. The 10k and 12k tiers keep the face at 100%. | At 8k, the MakeHuman face (about 5.3k triangles with eye and mouth rims) would otherwise leave about 2.7k triangles for everything else. |
| D-021 | PS2 body render vertices are unique (hm08 vertex, UV) pairs; `sourceVertex` maps each to exactly one hm08 body vertex. Normals come from the dense hm08 mesh and are gathered per render vertex. | Keeps hm08 UV seams sharp (every MakeHuman skin still fits) while lighting stays smooth across seams. |
| D-022 | MHCLO assets with shear transforms are skipped (1 garment: `toigo_female_suit`). | No other shipped asset uses shear; supporting it needs `affine_matrix_from_points`. This can be revisited if needed. |
| D-023 | Only CC0 packs are fetched for now; CC-BY packs are not used yet. | No CC-BY asset was needed so far, and the licence collector already supports attribution rows when one is added. |
| D-024 | Garments get a collision step after MHCLO fitting (`packages/core/src/proxy/collision.ts`). Each garment vertex within 5 cm of the visible body is anchored to up to 3 body triangles. On every refit it is projected onto them and pushed out to 1.5 mm, and the push spreads to 2 rings of neighbours at half strength. Anchors are rebuilt on the current shape whenever it settles (not during a drag; `CharacterEngine.interacting`), so the result depends only on the shape, never on edit history. Closest points on the open edge around hidden faces are ignored. | MakeHuman has no collision. Measured before the fix, 60 of 116 garments sat up to 23 mm inside the skin on random bodies, and 54 already did on the default body (collars in necks, flats in feet). After it, the deepest of 400 garment fits is 1.3 mm (PRD limit 2 mm). Cost: about 0.3 ms per frame, 24 ms to re-anchor 3 garments. The median garment moves at most 1.7 mm; the worst case (casualsuit01 collar) moves up to 23 mm on 7% of its vertices. |
| D-025 | On PS2 bodies, a body triangle is hidden when at least 2 of its 3 corners are in `delete_verts`, or all 3 are in computed coverage. The any-vertex rule (D-013) applies only to the hm08 fallback. | PS2 body triangles are much larger than hm08 faces, so one deleted corner cut visible holes well past the garment edge (shoulders, sleeves). Requiring all 3 corners left too much skin under thin garments (7 mm poke-through on short gloves). Two corners plus D-024 passes the 2 mm test. Thin slivers can remain at some garment edges (noted in STATUS). |
| D-026 | Garments without MakeHuman `delete_verts` (34 of 116) get hidden faces computed at build time (`tools/asset-tools/src/coverage.ts`). A body vertex is covered when all 7 rays of a 30° cone around its normal hit opaque cloth (texture alpha ≥ 0.9) within 4 cm. The covered set is eroded by one ring, and see-through materials (transparent with opacity < 0.9) cover nothing. Review images are in `docs/milestones/M4/hidden_faces/`. | This follows the PRD's "raycast from body vertices; hide faces fully covered". Sampling alpha keeps fishnets and lace from hiding skin through their holes, and the cone plus erosion keep loose hems (skirts) from hiding legs. Result: 24 garments get computed faces, and 10 (fishnets, sheer stockings, one hat) correctly hide nothing. |
| D-027 | UV templates use the texture convention: image row 0 is UV v = 1, pixel = floor(uv × 1024), and UV 1.0 maps to the last pixel. The core rasteriser (`renderUvTemplate`) is pure TypeScript and pixel-tested. The app draws it over the current texture and saves it through a Save dialog (`SaveImageAs`). | This matches how the viewport samples textures (flipY), so a texture painted on the template lines up when dropped back on the garment. |
| D-028 | The golden oracle needs two additions to run MakeHuman headless. First, `G.app` is a stub exposing only `selectedHuman`, because `skeleton.py` reads the human through it. Second, `updateMacroModifiers()` runs after `resetMeshValues()`, as the GUI's modifier task view does after a reset. | Without the second, MakeHuman's reset leaves the target stack empty, so the "default" golden character was the raw base mesh, not what MakeHuman shows (5 cm off). After both fixes, every golden test passes: vertices 1.7e-5 m, joints 8.6e-6 m, proxies 2.7e-5 m. |
| D-029 | **PRD correction:** the card-hair scalp is the head skin (body faces dominated by the head bone, inside the widest hairline preset), not MakeHuman's `helper-hair` geometry. | Measured: `helper-hair` is a volume helmet 4 to 60 mm off the skin (median 9 mm on top, 35 mm at the back) that also runs down the back for long hair. Roots and the scalp shell placed on it floated off the head. |
| D-030 | The built-in card atlas is MakeHuman's CC0 `long01` hair texture. Alpha detection finds its 2 opaque areas, and the build splits each at its midline into the 4 mirrored strips the texture holds, tagged clump, base, fringe and flyaway. It is embedded in `catalog.json` (`hairAtlases`). | Alpha cannot separate strips joined by opaque pixels; a user would split them in the atlas editor. It is real CC0 art (nothing faked), but it is not a purpose-made card sheet (see TODO_ART). |
| D-031 | New characters default to the 8k body tier (was 12k). Saved characters keep their tier. | A 12k body alone fills the 12k default budget, so any hair pushed a character past the 15k hard maximum (a 12k body, Bob hair and eyes total 15.2k). The PRD's budget-bar mockup shows a 7.9k body. |
| D-032 | Card hair is regenerated on the current body whenever the shape settles, and follows the body through its binding during a drag (the same rule as D-024's anchors). Roots are chosen on the neutral mesh, so the card topology never depends on the body. The collision proxy's shapes are shrunk until the scalp lies outside them. The binding keeps offsets along the triangle edges (they scale) and along the unit normal in metres (they do not), and card root corners are snapped onto the scalp. | Regenerating gives exact collision on every head (the 200-head test), while the binding keeps drags cheap and attached (root gap change under 3 mm). MakeHuman's head-scale sliders reach only +17%, so the attachment test also applies an exact +20% scale of the head. |
| D-033 | Route A hair meshes are decimated at build time to the 3,500-triangle hair budget with the garment decimator. 33 of 35 fit; 2 remain over budget and are flagged. | PRD F5 route A: "decimate them to budget". Some MakeHuman hair meshes had up to 91k triangles. |
| D-034 | **PRD correction:** the head texture split packs each head UV island separately (one uniform scale for all, a per-island offset) instead of using one affine map from the head's bounding box (`packages/core/src/skin/headsplit.ts`). Each PS2 body triangle goes to the head or body material by the UV island of its corners. | In hm08 the head is 4 UV islands spread across the layout (face/scalp/neck, mouth interior, two eye sockets), so one bounding box would cover almost the whole texture. With packing, the head gets 1.45x the body's texel density at 1024 px. All head UVs stay inside 0..1, islands never overlap, and every PS2 triangle has exactly one material (tested on all three tiers). |
| D-035 | Skin layers are blended on sRGB-encoded 8-bit values, as image editors do. Each layer is one pass, rounded to 8 bits: `result = below + (B(below, layer) - below) * alpha * opacity * mask`. The GPU compositor writes a plain RGBA8 render target, and the body shader decodes it with the exact sRGB curve (`uMapRaw`). The core reference compositor (`skin/blend.ts`) defines the result; the GPU must match it within 2 levels. | This matches what users expect from Photoshop-style blend modes, and keeps the GPU and the reference comparable. Measured on an 18-layer synthetic stack (every mode, masked and not, HSV adjustments): at most 2 levels off, on 27 of 262,144 values (float32 against float64 rounding). The real 2048 px stack is at most 1 level off. |
| D-036 | Procedural layers (dark circles, eye bags, stubble, lips, eyeliner/eyeshadow, blush, freckles, dirt, bruises, sweat) are functions of the neutral hm08 surface: position and normal per texel, plus facial features measured on the mesh itself. The eye and lip rims are the seams between the face island and the eye and mouth islands. The layers are drawn at 1024 px and filtered up to the 2048 px composite. | Placement in 3D crosses UV seams without a break, and the layers stay put when the body morphs. They are stand-ins until the user paints overlays (TODO_ART). Each takes 30 to 250 ms and is cached per settings. |
| D-037 | MediaPipe Face Landmarker is bundled in `assets/core/vendor/mediapipe/`: the WASM runtime from the pinned npm package `@mediapipe/tasks-vision` 1.2.2, and `face_landmarker.task` (float16/1). The model is fetched once at build time and pinned by SHA-256 in `sources.lock.json`. It runs on the CPU delegate. The licence manifest now also allows Apache-2.0 for bundled runtime software, with its NOTICE. | PRD 3: "bundle the WASM and .task model locally (no CDN)". There is no network call at runtime. Apache-2.0 is not an art licence, so the policy text separates the two. |
| D-038 | The landmark table (`assets/core/skin/landmarks.json`, built by `pnpm build:landmarks`) keeps the PRD's nearest visible vertex per landmark. It also adds an exact surface anchor: the three hm08 vertices and barycentric weights of the ray hit. Projection uses the anchors. The 10 iris landmarks stay unmapped. | Measured on the render, the nearest vertex is a median 1.1 mm and up to 5.7 mm from the landmark, which is up to about 11 texels at 1024. The anchors reproduce the landmarks exactly. |
| D-039 | Photo projection (`skin/photo/project.ts`) weights each texel by how much it faces the camera, and fades out over 12% of the face width towards the edge of the landmark hull. It skips texels hidden from the front, using a depth buffer of the body, so the mouth interior, nostrils and under-chin get no photo. It drops triangles that fold over in the photo. The photo layer is composited directly above the base skin, under the overlay layers. It is re-projected when the shape settles and the landmark vertices moved more than 0.1 mm. Landmarks are stored in the character document, so loading a character never needs the detector. | PRD F7 steps 4 and 5. Makeup and dirt layers must stay on top of the projected face. |
| D-040 | The frontal-pose check uses MediaPipe's facial transformation matrix; the plane of the face oval is only a fallback. | The oval plane reads about 20° of pitch on a straight-on face. MediaPipe also reads MakeHuman's own renders as tilted 16 to 17° even when they are straight on, because the head's neutral posture differs from MediaPipe's canonical face. So a render used as a "photo" can show the tilt warning; real photos should not. |
| D-041 | M6 projection acceptance measures on a front render of the body only, unlit, with no eyeballs, brows or lashes. The error is the pixel distance between each re-found landmark and its anchor, converted to texels with the feature's own scale (the UV distance between its two corners over their pixel distance). Until the user supplies photos in `docs/milestones/M6/test_photos/`, 5 renders of other MakeHuman characters stand in. A control photo, misregistered on purpose by 4% of its width, must fail the check. | With the eyes and lashes visible, MediaPipe follows the mesh's eye and mouth openings rather than the painted photo, and a misregistered photo still passed (2.5 texels). Measured on the skin alone, the 5 stand-ins are within 2.05 texels and the control reads 6.1. |
| D-042 | **Fix to M3 (PS2 body meshes):** vertices within 5 mm of the mouth and eye corners are now locked during simplification. All three tiers were rebuilt: 8,000 / 10,000 / 12,000 triangles, face retention 95.8% / 100% / 100%, no flipped faces. | The rule "lock vertices near eye and mouth openings" (PRD F2) measured from MakeHuman's `joint-mouth`, which sits about 8 cm back inside the mouth, so it never reached the lips. The 8k tier had moved the right mouth corner: 5 texels off in the projection check before any photo was applied. A 10 mm lock broke the 8k budget (9.4k triangles). |
| D-043 | The FBX writer (`app/backend/fbx`, binary FBX 7.4 after Blender's `io_scene_fbx`) writes: Y up, +Z front, metres (`UnitScaleFactor` 100, which is in centimetres); bones as `LimbNode` models with local translation and Euler XYZ rotation; one mesh model per material group, whose control points are the render vertices with normals and UVs mapped `ByVertice`; one skin cluster per bone that has weights in that mesh; and a bind pose covering all bones and meshes. Object ids are sequential and arrays use a fixed zlib level, so output is deterministic. The top-level `CreationTime` is Blender's constant `1970-01-01 10:00:00:000` (the real time goes in `CreationTimeStamp`). Bones whose bind matrix is not a rotation plus translation are rejected. | The Autodesk FBX SDK (Unity's importer) checks the fixed footer id against `FileId` and that `CreationTime`; with the real time there, Unity reported all 10 test files as corrupted while ufbx loaded them. Fuzzing found that a sheared bind matrix cannot round-trip through FBX node transforms; the engine's bones are always rigid. |
| D-044 | Each export has at most 5 meshes, one material each: Head, Body, Hair, Garments (merged into one atlas) and Eyes (eyes, brows, lashes and teeth in one atlas). Garment tint, brightness and dirt, and brow and lash density, are baked into the atlases; part UVs are clamped into their atlas cells (MakeHuman garments overshoot 0..1 by at most 1.3%). Hair keeps its own texture, so tiling hair UVs still work. The feet are put on the origin using the exported body's lowest vertex. | PRD 6.2 asks for "one SkinnedMeshRenderer per material group" and at most 5 draw calls. Several garments with their own textures would otherwise need several draw calls. |
| D-045 | The Unity importer builds the Humanoid `HumanDescription` from `humanoid_map.json` plus the sidecar's skeleton in a T-pose (both upper arms rotated level), with FBX coordinates converted to Unity's by mirroring X. Materials and the prefab are created in `OnPostprocessAllAssets`. The humanoid map is read from the package's resolved folder on disk. | With the A-pose as the reference pose, retargeted animations would hold the arms too low; this is what Unity's "Enforce T-Pose" button fixes by hand. The AssetDatabase had not yet imported the package's JSON when the first FBX was preprocessed, which left every avatar without bones. |
| D-046 | The M7 retarget check in the Unity harness uses a walk cycle built from Humanoid muscle curves, applied through `HumanPoseHandler` (Mecanim's muscle space, the same path any Humanoid clip takes), plus any clips you put in `tests/UnityHarness/Assets/Animations`. Hard checks: avatar valid and Humanoid; at most 5 renderers with the right shaders and textures; triangles equal to the sidecar and within budget; blendshapes present; feet at y = 0; facing +Z; left on the left; rest-pose skinning reproduces the mesh within 1 mm. Pose renders go to `docs/milestones/M7/unity/` for the screenshot check. | No Mixamo or Unity sample clip is available offline (Mixamo needs an account). Unity does not re-skin meshes for a manual camera render in the editor, so the harness renders baked copies of each pose. Triangle stretch in a stride is reported, but only gross values (over 50x) fail: crotch and armpit triangles legitimately stretch up to about 15x. |
| D-047 | The GLB is written with Three.js GLTFExporter, with the skeleton root and the skinned meshes as top-level nodes, and checked with the Khronos glTF-Validator (`gltf-validator` 2.0.0-dev.3.10, Apache-2.0). Any error fails the export. | With a wrapper node above the skinned meshes the validator warned `NODE_SKINNED_MESH_NON_ROOT`; now there are 0 errors and 0 warnings on all 10 test characters. |
| D-048 | ufbx is pinned at v0.23.1 (commit `26a482ae`, vendored in `app/backend/fbx/ufbx`, MIT or public domain), not 0.20.x. Its cgo wrapper builds only with the `ufbx` build tag, and `pnpm test:go` runs the Go tests with it using the 64-bit mingw-w64 compiler. | v0.23.1 is the current release. The tag keeps `wails build` and plain `go test` free of a C compiler; the 32-bit MinGW.org gcc is still first on the PATH. |
| D-049 | **Fix to M6:** the GPU skin compositor now binds a neutral texture to the inputs a pass does not read. Previously the base pass kept sampling the render target from the previous composite's last pass while writing into it. | WebGL treats that as a feedback loop and silently skips the draw, so after the first composite each change of layers piled onto the previous result (an export showed one character's dirt layer on later characters). The M6 test composited only once and missed it; it now checks 5 sequential stacks against the reference. |
| D-050 | Expression blendshapes are baked from MakeHuman's 60 face pose units (`face-poseunits.bvh`) on its default rig, ported exactly: the BVH is read Z-up as `bvh.py` does, units are blended like `PoseUnit.getBlendedPose` (slerp from identity, multiplied in order), joints are the mean of their vertices, weights are normalised with MakeHuman's 1e-4 cut, and each unit rotates a bone in world axes about its head. A golden test against MakeHuman's own posing on 3 characters matches within 6e-7 m. The default set is mapped straight to pose units in `packages/core/src/data/expression_map.json`; MakeHuman's 32 `.mhpose` expressions are not used. | No source we fetch contains the `.mhpose` files (the asset pack index lists none; makehumancommunity.org announced its community services shut down on 2026-10-21), and the PRD allows mapping the defaults to pose units directly. The pose units are in the pinned MakeHuman source (CC0). |
| D-051 | Blendshapes move every part they affect: the PS2 head and body take the base-mesh deltas through their vertex map; eyes, brows, lashes and teeth are skinned to the default rig with weights transferred through their MHCLO binding (how MakeHuman poses proxies, so lashes turn with the lid); garments, mesh hair and card hair follow the skin point they are bound to. Each mesh exports only the shapes that move it by over 1 um, with normal deltas. A T-pose export turns the deltas with the arm skinning. | PRD F8: brows, lashes and the hair shell must receive the same blendshapes. Rotating loose parts (hair far from the scalp) about face bones would swing them; following the bound skin point keeps them attached. |
| D-052 | `blink_L` and `blink_R` are the upper-lid unit plus 0.3 of the lower-lid unit, with the upper-lid weight calibrated per character: the smallest weight from 1.0 to 1.45 (steps of 0.05) at which no view ray (12 directions, 41 x 41 rays each) reaches the eyeball before the skin. The calibration runs when the shape settles (not during a slider drag). | MakeHuman's lid units turn the lid by a fixed angle, so on some eye shapes the lid stops short and a sliver of eyeball shows (up to 17 rays on extreme random characters at weight 1). Rotating further than needed opens a gap again as the lids pass each other, so the search stops at the first closed weight. |
| D-053 | M8 acceptance definitions. Blink "closes fully": zero rays reach the eyeball from the 12 views. "Without lashes intersecting the eyeball": with the eye closed, the blink adds no lash crossings of the eye surface that can be seen (MakeHuman's lash roots already sit inside its low-poly eye shell at rest, 35 to 42 edges, all behind the lid). jawOpen "without tearing": vertices that coincide at rest (UV seams, the head/body split) move identically; no edge outside the parting lips stretches over 4x; folded triangles stay within 12 mm of the mouth opening and under 1 cm2 in total. MakeHuman's own JawDrop folds the same lip triangles on its full mesh (0 to 22 per character). | These are measurable versions of the PRD's wording. Part-way through a blink, linear blendshapes and MakeHuman's own rotations both let a few lash edges dip into the eye surface (reported per weight in `expression_report.json`); in-between blendshape frames are not exported. |
| D-054 | Character browser (File -> Characters..., Ctrl+O): every saved character with a 256 x 320 full-body thumbnail written to `Characters/<name>/renders/thumb.png` on each save, to open or duplicate (a copy gets a new id and name and its own thumbnail). The asset server serves only `/characters/<name>/renders/thumb.png` from the Characters folder. | PRD F10. Documents and exports in the Characters folder stay unreachable from the WebView. |
| D-055 | Save -> load -> export is byte-identical (PRD M9). Three things had to change: `serializeCharacter` writes the parsed (canonical) document, so loading gives back exactly what was saved (key order of `hair` differed); loading no longer renormalises an ethnic mix that already sums to 1 (it moved the last bit of a value that feeds the morph weights); and the GLB is rewritten into a fixed layout after GLTFExporter (`app/frontend/src/export/glb-canonical.ts`), which otherwise appends embedded images in the order their PNG encoding finishes, so two GLBs of the same scene differed. | Found by the round-trip test. The GLB fix also makes two exports in one session identical. |
| D-056 | The installer (Wails NSIS, `app/build/windows/installer/project.nsi`) installs per user, without administrator rights, to `%LOCALAPPDATA%\Programs\PS2CC`, ships `assets/core` (all of it, 275 MB, so `LICENSES.json` covers every file) next to `PS2CC.exe`, and compresses with solid LZMA. Install and uninstall never touch `Documents\PS2CC` or the logs. NSIS is 3.11 (portable zip in `tools/.toolcache`, TOOLCHAIN.md). | An internal tool should install without an admin prompt. The app already looks for `assets/core` next to its exe. Windows 11 ships the WebView2 runtime; the Wails bootstrapper (network) only runs if it is missing. |
| D-057 | The desktop acceptance test (`pnpm test:desktop`, `e2e/tools/desktop.spec.ts`) drives the app under `wails dev` with a temporary `PS2CC_HOME`: the real Go backend and the real frontend, through the dev server. It ends the Go process with TerminateProcess to simulate a crash. Vite's dev port moved from 34115 to 34116 (Wails' dev server uses 34115), and Vite returns 404 for `/library` and `/characters` so Wails hands them to the Go asset handler. `Info()` reports the process id. | The WebView2 in the built exe cannot be automated from outside: Wails clears `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` before creating it, on purpose. The installed exe is covered by `pnpm test:installer` (install, start, uninstall) and the manual clean-VM check. |
| D-058 | First-run setup asks for the Unity project (typed or browsed; checked for `Assets/` and `ProjectSettings/ProjectVersion.txt`, the Unity version is shown) and the triangle budget, and stores them in `settings.json`. New characters start from the settings (budgets, texture sizes, Unity project). A restored autosave is marked unsaved. | PRD M9 "first-run setup (Unity project path)". |
| D-059 | An imported garment is an ordinary proxy asset (`packages/core/src/proxy/garment-import.ts`), stored as `Library/garments/<stem>_<id>.json/.bin`, id `user:garment/<stem>_<id>`.
